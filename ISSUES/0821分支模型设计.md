# 完成事项

## 构建本项目的 harness —— 多人多 agent 协作流程中分支模型的设计

### 启用分支模型：GitHub Flow

```plaintext
main                       ← 唯一真相源 / 发布版本,受保护,打 `SemVer tag`
 │  ↑ release → main + tag,然后删旧 release、切新 release
 │  ↑ hotfix → main + tag（紧急快车道,跳过 release 静置）
 │  ↓ main → develop（单向同步,develop 永不落后 main）
 │
release/vX.Y.Z             ← 预发布,一次性,code-review 门禁
 │  ↑ feature PR → release（测试通过后,人决定这轮发哪些）
 │
develop                    ← 日常开发调试沙箱,集成测试,不丢弃;退出功能用 revert 或重建
 │  ↑ feature → develop（CI,日常测试）
 │
feature/* fix/*            ← 从 main 切，发布前不删
hotfix/*                   ← 从 main 切,紧急修复直达 main + tag
```

流转：

```plaintext
feature/x（从 main 切）
   → develop（测试 + CI）
   → 测过 → PR 到 release（code-review 门禁）
   → release → main + tag
   → 删旧 release、切新 release
   → main → develop 同步
```

|类型|从哪切|去哪|门禁|版本|
|:-|:-|:-|:-|:-|
|feature/*|develop|main|code-review|feat→MINOR|
|fix/*|main|develop|code-review|fix→PATCH|
|hotfix/*|main|main + develop|CI+快速 review|PATCH + tag|
|release/vx.Y.Z|develop|main|code-review + 打tag|打tag|

> 后期如果有版本号、定期发布的需求的话启用 Git Flow

### 启用 CI，持续集成

就是代码推到 GitHub 后，服务器自动跑检查。

```plaintext
你 push / 开 PR
   ↓
GitHub Actions 启动一台临时机器
   ↓
跑 npm install && npm run check:all
   ↓
PR 页面显示 ✅ 或 ❌
   ↓
❌ 时禁止合并（配合分支保护规则）
```

### 冲突处理规则

|冲突类型|处理方|做法|
|:-|:-|:-|
|package-lock.json|AI|删掉重跑 `npm install`|
|claude/skills/./cursorignore|AI|run 等同步产物 `sync:agent`|
|不同文件的改动|Git自动|无需干预|
|同文件不同区域|AI|保留双方|
|同一函数双方都改|人|AI停下，列出双方意图，等人决策|
|语义冲突（无文本冲突但逻辑打架）|AI|只能提示风险|

### 多 agent 并行，启用 worktree

在 AI 时代：

不用 `worktree` ，两个 AI agent 同时改代码会互相覆盖文件、index.lock 冲突。

用 `worktree`，每个 agent 一个独立目录 + 独立分支 → 物理隔离，零冲突。

```bash
# agent A 做功能 X
git worktree add ../chatbot-featx -b feat/x main
cd ../chatbot-featx && npm install

# agent B 做功能 Y（同时）
git worktree add ../chatbot-featy -b feat/y main
cd ../chatbot-featy && npm install
```

每个 agent 在自己目录工作，互不干扰。完成后各自开 PR。

> 注意：.husky/post-checkout 会在 worktree 创建时触发 sync，这是对的。
