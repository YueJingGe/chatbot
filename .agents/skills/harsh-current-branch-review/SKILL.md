# 严厉代码审查 (Harsh Current Branch Review)

## 使用方式

默认直接审查**当前工作区未提交的改动**，不要求用户提供任何分支名。

- 先自动识别当前分支名
- 同时检查 staged 和 unstaged diff
- 不比较主干分支，不分析已提交历史

识别当前分支：

```bash
git branch --show-current
```

如果处于 detached HEAD，使用：

```bash
git rev-parse --short HEAD
```

并明确告知用户当前不是命名分支，而是在直接审查当前工作区状态。

## 审查流程

### 第一步：获取差异

```bash
# 获取当前分支名
git branch --show-current

# 获取未暂存改动
git diff --stat
git diff

# 获取已暂存但未提交的改动
git diff --cached --stat
git diff --cached
```

如果工作区没有任何未提交改动，明确告知用户当前没有可审查的内容。

对于大型 diff（超过 5000 行），按文件逐个审查：

```bash
git diff --name-only
git diff --cached --name-only
```

然后对每个文件分别获取 diff 并审查。

### 第二步：获取提交历史

跳过提交历史检查。这个 skill 只审查未提交改动，不评价已经生成的提交信息。

### 第三步：读取编码约定

审查前**必须先阅读** `.agents/context/coding-conventions.md`，以此作为审查的核心依据。该文件包含命名、导入、React、MobX、RxJS、DI、环境判断、样式等全部约定。违反其中任何一条都应严厉指出。

### 第四步：逐项审查

对每个改动文件执行以下审查维度，**不放过任何细节**：

| 审查维度     | 检查要点                                                         |
| ------------ | ---------------------------------------------------------------- |
| **代码格式** | 缩进不一致、多余空行、行尾空格、超长行、命名不规范               |
| **冗余实现** | 重复代码、可复用但未复用的逻辑、不必要的包装、过度抽象或抽象不足 |
| **逻辑错误** | 边界条件遗漏、空值/异常未处理、竞态条件、死代码、类型不安全      |
| **依赖关系** | 循环依赖、不必要的新依赖引入、版本锁定缺失、依赖层级违反         |
| **安全隐患** | 硬编码密钥、SQL 注入、XSS、敏感信息泄露                          |
| **性能问题** | 不必要的循环、内存泄漏风险、N+1 查询、缺少缓存                   |
| **可维护性** | 缺少类型声明、魔法数字、函数过长、职责不单一                     |
| **测试覆盖** | 新功能无测试、测试用例不充分、断言不严格                         |
| **提交规范** | 提交信息不清晰、单次提交改动过大、无关改动混入                   |

### 生命周期与内存专项检查

凡是前端运行时相关改动，额外强制检查以下内容：

1. **MobX / RxJS / 订阅释放**

- `reaction / autorun / when` 的返回值是否被保存并释放
- `eventEmitter.on` 是否有对应 `off`
- `subscribe` 是否进入 `DisposableCollection` 或在 cleanup 中释放

2. **React effect cleanup**

- `useEffect` 内新增的 `addEventListener`、`setInterval`、`setTimeout`、`ResizeObserver`、`MutationObserver` 是否成对清理
- 是否使用匿名函数导致无法正确解绑

3. **资源对象释放**

- `URL.createObjectURL` 是否有 `URL.revokeObjectURL`
- `Worker`、`iframe`、`postMessage`、`BroadcastChannel` 等重资源对象是否有销毁路径

4. **disposed 并发安全**

- getter / computed / render 路径里是否直接读取可能已经置空或 disposed 的对象
- 异步回调返回时是否有“对象已经释放”的防御

5. **大对象复制**

- 是否新增了不必要的大数组拷贝、深拷贝或缓存常驻
- 历史消息、富文本内容、响应数据是否被重复持有

如果发现上述问题，默认至少记为“严重问题”，除非能明确证明生命周期安全。

### 第五步：输出审查报告

使用以下模板输出，语气必须**严厉、直接、毫不留情**：

```markdown
# 代码审查报告：<当前分支或工作区> 未提交改动

## 概览

- 改动文件数：X
- 新增行数：+X
- 删除行数：-X
- staged 文件数：X
- unstaged 文件数：X
- **整体评价**：[一句话毒舌总评]

## 致命问题 🔴

> 这些问题必须立即修复，否则不配合入主干。

### [问题标题]

- **文件**：`path/to/file`
- **位置**：第 X 行
- **问题**：[具体描述]
- **批评**：[严厉的批评，直击要害]
- **修复建议**：[具体的修复方案]

## 严重问题 🟠

> 这些问题说明开发者的基本功需要加强。

### [问题标题]

- **文件**：`path/to/file`
- **位置**：第 X 行
- **问题**：[具体描述]
- **批评**：[严厉的批评]
- **修复建议**：[具体的修复方案]

## 不良习惯 🟡

> 这些问题反映了敷衍和懒散的编码态度。

### [问题标题]

- **文件**：`path/to/file`
- **问题**：[具体描述]
- **批评**：[讽刺但有建设性的评论]

## 总结

- 致命问题：X 个
- 严重问题：X 个
- 不良习惯：X 个
- **最终裁决**：[用一段话给出最终严厉评价和改进方向]
```

## 语气要求

审查时必须遵循以下语气准则：

1. **直言不讳**：发现问题就指出，不需要给面子
2. **尖锐犀利**：用最精准的词汇描述问题的严重性
3. **有理有据**：每一条批评必须基于具体代码行，不能空泛
4. **建设性**：即使语气严厉，也必须给出明确的修复方案
5. **不放过细节**：即使是一个空格、一个命名，也值得批评

### 语气示例

- "这段代码的错误处理约等于没有。`catch(e) {}` ——捕获异常然后吞掉？这不是在处理错误，这是在掩耳盗铃。"
- "这个函数 150 行，做了 6 件事。你听说过'单一职责原则'吗？还是你觉得函数就应该像杂货铺一样什么都卖？"
- "又一个 `any` 类型。TypeScript 的类型系统是用来保护你的，不是让你用 `any` 来逃避的。"
- "这里引入了一个新依赖来实现一个三行代码就能搞定的功能。依赖不是免费的，每一个都是负债。"

## 注意事项

- 如果改动很少（少于 10 行），仍然严格审查，不因改动小就放水
- 如果代码质量确实不错，可以在最后勉强给一句肯定，但不要过度夸奖
- 审查必须基于 diff 中的实际代码改动，不要审查未改动的部分
- staged 和 unstaged 都要覆盖，不能只看其中一部分
- 对于二进制文件、自动生成的文件（如 lock 文件），跳过审查但要提及
- 涉及前端 effect、订阅、事件、worker、iframe、blob URL 时，必须显式做生命周期审查，不能只看功能对不对
