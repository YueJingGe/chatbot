# Create Bugfix — Bug 修复记录生成

## 触发场景

- 用户描述了某个 Bug 现象（报错、异常行为、UI 异常等）
- 用户要求修复某个问题并生成修复记录

## 工作流程

严格按以下四步顺序执行，每步完成后在文档中记录结果。

### Step 1: 定位

**目标**：找到 Bug 的精确位置。

1. 从用户描述中提取关键信息：
   - 错误信息 / 堆栈追踪
   - 复现步骤
   - 预期行为 vs 实际行为
   - 影响范围（哪个页面、哪个组件、哪个接口）
2. 搜索项目代码，定位可疑文件和代码行
3. 使用 Grep / SearchCodebase / LSP 等工具缩小范围
4. 记录定位结果：涉及的文件路径和行号

如果信息不足以定位，使用 AskUserQuestion 向用户确认（最多 2 个问题）。

### Step 2: 分析

**目标**：理解根因，而非表面现象。

1. 阅读定位到的代码上下文（前后至少 20 行）
2. 追踪数据流 / 调用链，找到根本原因
3. 判断 Bug 类型：
   - 逻辑错误（条件判断、边界值）
   - 状态管理问题（状态不同步、竞态）
   - 样式问题（CSS 覆盖、响应式）
   - 接口问题（参数错误、返回值处理）
   - 环境问题（配置缺失、版本不兼容）
4. 评估影响范围：是否有其他地方存在相同问题
5. 记录根因分析结论

### Step 3: 修复

**目标**：以最小改动修复问题，避免引入新问题。

1. 制定修复方案（如有多种方案，选择改动最小、风险最低的）
2. 实施修复，遵循项目编码规范
3. 修复原则：
   - 只改必须改的代码，不做额外重构
   - 保持与周围代码风格一致
   - 如需添加临时方案，标注 `// TODO: ...` 或 `// FIXME: ...`
4. 记录修复内容：改了什么、为什么这样改

### Step 4: 验证

**目标**：确认修复有效且未引入新问题。

1. 执行构建验证：`npm run build`（或项目对应的构建命令）
2. 如有测试用例，运行相关测试
3. 确认修复覆盖了 Step 2 中识别的所有影响点
4. 检查是否有副作用
5. 记录验证结果

## 生成文档

四步完成后，按以下模板生成修复记录：

```markdown
# Bug 修复记录 — {简述}

## 基本信息

| 项目 | 内容 |
|------|------|
| 修复日期 | YYYY-MM-DD HH:mm |
| Bug 严重程度 | P0/P1/P2 |
| 影响范围 | |
| 状态 | 已修复 |

> 严重程度定义：P0 = 系统崩溃/数据丢失 | P1 = 功能不可用 | P2 = 体验问题

---

## 一、Bug 描述

### 现象
[用户观察到的异常表现]

### 复现步骤
1. ...
2. ...
3. ...

### 预期行为
[正确的行为应该是什么]

### 实际行为
[实际发生了什么]

---

## 二、定位

### 涉及文件
| 文件路径 | 行号 | 说明 |
|----------|------|------|
|          |      |      |

### 定位过程
[如何一步步缩小范围找到问题]

---

## 三、根因分析

### Bug 类型
[逻辑错误 / 状态管理 / 样式问题 / 接口问题 / 环境问题]

### 根本原因
[详细解释为什么会出现这个 Bug]

### 影响评估
[是否有其他地方存在相同问题]

---

## 四、修复方案

## 六、变更文件清单

| 文件路径 | 变更类型 | 变更说明 |
```

## 保存文件

**文件命名规则**：`YYYY-MM-DD-HH-mm-bugfix-简述.md`

- 日期时间取当前系统时间
- 简述使用简短中文或英文，概括 Bug 核心问题
- 示例：`2026-08-17-14-30-bugfix-消息列表未滚动.md`、`2026-08-17-09-00-bugfix-login-401.md`

**存储路径**：`{workspace}/Documents/需求分析/BugFix/`

- 路径相对于工作区根目录
- 若目录不存在，先创建再写入

## 注意事项

- 四步流程必须按顺序执行，不可跳过任何步骤
- 修复前必须完成定位和根因分析，禁止"猜测式修复"
- 修复改动应保持最小化，禁止搭车重构
- 验证步骤必须执行构建命令，不可仅凭目测判断
- 经验总结应提炼出可复用的规则，而非泛泛而谈
- 如修复过程中发现新 Bug，单独记录，不在本文档中处理
